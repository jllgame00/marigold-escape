# 「왕비 후보의 서찰」 독립 UX/UI 리뷰

- 리뷰일: 2026-09-21
- 대상: 현재 워킹트리의 모바일 웹 구현. 직전 작업의 스크롤 전환 수정도 포함한다.
- 목적: 행궁동 현장에서 스마트폰으로 읽고, 이동하고, 관찰하고, 해결하는 경험을 평가한다.
- 범위: 분석 및 이 문서 작성만 수행했다. 애플리케이션 코드·CSS·설정·데이터를 수정하거나 commit/push하지 않았다.

## 0. 검토 방법과 판단의 한계

### 실제로 확인한 것

실행 진입점인 src/main.jsx, src/App.jsx의 전체 화면 분기·스토리·미션·퍼즐, src/styles.css의 모든 선언과 후속 override, src/index.css, 랭킹 컴포넌트·서비스, 시간 평가 함수, index.html, Vite 설정, 정적 자산 목록과 크기를 읽었다. 문단 수, 정적 색상 대비, 주요 이미지 헤더 크기는 읽기 전용 계산으로 확인했다.

실제로 사용하는 storyFlow는 **App.jsx 안의 배열**이다. src/data/gameData.js에도 별도 storyFlow가 있지만 App은 그 파일의 gameInfo만 가져온다. 따라서 그곳의 짧은 프롤로그, 메리골드 위치 정보, TEMP 정답을 현재 UI로 오인하지 않았다. App.css 역시 현재 진입점에서 import하지 않아 평가 대상 스타일에서 제외했다.

브라우저 연결을 확인했으나 사용 가능한 브라우저 목록이 비어 있었다. 따라서 **실제 렌더, 스크린샷, 모바일 키보드, iOS 뒤로가기, 현장 카메라 인식률은 검증하지 못했다.** 기본 이미지 뷰어는 환경 오류가 있었지만 읽기 전용 이미지 출력으로 Poster, 매듭 퍼즐 바탕, Story 7/Ending 포스터 원본은 직접 확인했다. 이는 브라우저에서 합성된 UI를 확인한 것과 다르다. 영상 내용과 미확인 자산을 직접 본 것처럼 평가하지 않는다. 360/390/430px 평가는 CSS와 자산 크기에 근거한 예측이며 실기기 테스트 결과가 아니다.

### 판정 표시

- **확정**: 코드·CSS·파일에서 직접 확인한 상태나 해당 상태로 결정되는 동작.
- **위험/추론**: 그 구현이 현장 사용자에게 줄 것으로 예상되는 영향.
- **현장 확인 필요**: 실제 장소·콘텐츠·기기에서만 판단할 수 있는 사항.

색 대비는 CSS 색상과 대표 배경 #120d12를 사용한 계산이다. 실제 배경은 그라디언트와 이미지가 있어 화면 전체에 대한 접근성 인증이나 실측값으로 읽으면 안 된다. 터치 영역 44–48px 제안도 이 서비스의 한 손 야외 조작을 위한 설계 목표다.

## 총평

**분위기와 기본 독서 화면은 갖췄지만, 현장 플레이용 인터페이스로서는 아직 진행 안정성과 행동 안내가 부족하다. 종합 5.2/10.**

문제는 색감이 고풍스럽지 않다는 데 있지 않다. 이미 밤색 배경, 금색 강조, 서찰의 밝은 면, 명조 본문이 서로 역할을 나누고 있다. 그러나 플레이어가 실제로 필요한 것은 다음 목적지, 지금 관찰할 대상, 막혔을 때의 도움, 돌아와도 보존되는 풀이 상태다. 현재는 이 정보와 안전장치보다 긴 서사와 문서 장식이 더 일관되게 구현되어 있다.

출시 전 해결할 핵심은 매듭 퍼즐의 숨은 방향 규칙, 단서첩 왕복 시 풀이 초기화, 사라진 힌트 진입, 일부 핵심 텍스트의 색 충돌, 일반 플레이에 노출된 임시 skip이다. 화면 상단으로 이동하는 공통 스크롤 처리는 이번 리뷰 기준 이미 구현되어 있으며, 예전 문제가 그대로 남았다고 평가하지 않는다.

## 1. 전체 UX Flow

현재 정상 경로는 Poster → Landing → Code → Team → Teaser → Prologue → Mission 1 → Story 2 → Mission 2 → … → Story 7 → Mission 7 → Ending → Clear → Coupon이다. flow는 티저·프롤로그·중간 스토리·7개 미션·엔딩을 합쳐 16개 노드다.

| 단계 | 지금 어디인지 | 다음 행동 | 정보량 | 전환과 앞뒤 역할 |
|---|---|---|---|---|
| Poster | 작품명·장르·행궁동·미션 7개가 이미지에 표시됨 | 첫 화면에는 아래로 내려달라는 안내만 있고 실제 버튼은 다음 섹션 | 이미지 하단 소개와 키워드는 모바일 축소 시 작아짐 | 안내 전인데 조사 준비가 끝났다는 표현이 성급하다. Landing과 두 번 입장하는 느낌 |
| Landing | 장르·시간·인원·준비물이 명시됨 | 조사 시작하기는 모든 안내 하단 | Hero, 안내, 키트, 주의사항으로 길다. 시간·인원은 중복 | 오리엔테이션 역할은 명확하나 Poster와 판매용 소개가 겹침 |
| Code | 입장 코드 입력이라는 제목과 키트 안쪽이라는 위치가 명확 | 서찰 열기는 기능과 서사가 맞음 | 적절. 테스트 코드 안내는 운영 화면의 신뢰를 낮춤 | 정상/오류 모두 한 화면. 도움 요청·키트 미보유 경로는 없음 |
| Team | 조사관 이름이라는 역할이 이해됨 | 티저 영상 보기로 도착점 예측 가능 | 적절하나 2글자 제한은 실패 후 알게 됨 | 코드 재입력 버튼이 큰 밝은 버튼이라 주행동과 경쟁 |
| Teaser | 작품 소개 영상 단계 | 사건 키트 개봉하기는 웹 이동인지 실제 봉투 개봉인지 모호 | 한 영상+짧은 설명 | 재생 완료 강제가 없어 유연하지만 필수 시청 여부가 설명되지 않음 |
| Prologue | 프롤로그와 제목이 있어 위치 식별 가능 | 다음으로는 목적지 정보가 없음 | 10문단·769자 | 티저 다음에 다시 긴 설정 설명. 실제 첫 이동은 다음 화면에서야 나옴 |
| Story 2–6 | 기록 번호·제목은 명확 | 특정 공방명 버튼과 추상적인 다음 실마리가 혼재 | 22–48문단. 문단 간격까지 합치면 길다 | 미션 결과를 서사로 풀어내지만 일부 시작 문장은 이미 한 조사를 다시 시작하는 표현 |
| Mission 1 | 미션 번호와 향기도예 표시 | 복원 → 카메라 → 선택지 제출의 다음 단계가 미리 보이지 않음 | 서찰·사건 기록·퍼즐·카메라까지 가장 복잡 | 퍼즐 성공과 미션 완료가 다르다는 점을 처음부터 알려주지 않음 |
| Mission 2 | 위치와 과제는 보임 | 구멍 연결 후 단서 확인 | 규칙은 짧지만 실제 정답 규칙 일부가 숨겨짐 | 방향 오답과 전체 초기화가 안내와 불일치 |
| Mission 3–7 | 목적지명/수수께끼와 조사 문제가 분리됨 | 관찰 후 입력은 비교적 명확 | 4는 변환표, 5는 여러 이미지, 7은 장소 추론이 부담 | 숫자·문장·동물 입력인데 입력 UI는 모두 동일 |
| Story 7 | 마지막 반전의 영상 화면 | 마지막 어찰 확인 → 실제로는 마지막 장소 미션 | 텍스트 3문단으로 급격히 짧아짐 | 영상에서 얻어야 할 정보와 다음 장소 찾기의 연결을 확인할 필요 |
| Ending | ENDING 표기와 혼례의 진실 제목으로 결말임을 알 수 있음 | 클리어 인증 보기는 역할이 분명 | 46문단·1,175자를 하나의 이미지 배경 카드에 배치 | 일반 story와 표면은 다르나 긴 텍스트 후에야 성과에 도달 |
| Clear | 첫 제목은 진실 확인. 개인 결과라는 인지가 늦음 | 쿠폰 버튼은 진실 요약·인증서·추천 공방 아래 | 서로 다른 목적의 5개 덩어리 | 결말 재요약 → 성과 → 추천 → 보상으로 다시 긴 경로 |
| Coupon | 쿠폰·사용처·기한·직원 제시 방식이 명시됨 | 실제 매장 제시보다 랭킹 버튼이 웹상 주행동 | 무엇을 받는지는 없음 | 보상 화면은 있지만 보상의 실체와 길찾기가 빠짐 |
| Clue Notebook | 단서첩 제목과 수집 상태는 명확 | 복귀는 전체 목록 하단 | 조사 목록과 수집 이름이 일부 중복 | 지도라는 이름인데 실제 지도·주소·재열람이 없음. 왕복 시 퍼즐 상태 손실 |
| Leaderboard | 오늘의 순위·기록임은 명확 | 각 행은 상세 보기, 마지막은 Clear 복귀 | 상세를 열면 매우 길어짐 | Coupon에서 들어왔는데 Coupon으로 바로 돌아가지 않음 |

## 2. First-Time User

첫 10초에 알 수 있는 것은 작품을 소개하는 포스터와 아래로 스크롤하라는 행동이다. 포스터 원본에는 조사관·미션 7개·공방거리 순회·웹 미션과 AR 단서 등 개요가 있어 소개 정보가 전혀 없는 것은 아니다. 그러나 941px 폭의 이미지가 360px 안에 축소되면 하단의 작은 소개와 키워드도 함께 작아지며, 이미지의 alt는 포스터 이름만 전달한다. 실제 시작 버튼은 100svh 포스터 뒤에 있다. 명시적 스크롤 안내는 장점이지만, 시작 준비가 된 현장 사용자가 곧바로 입장할 수는 없다.

첫 미션까지 Poster, Landing, Code, Team, Teaser, Prologue의 여섯 단계를 지나야 한다. 모두 다른 필요가 있지만 소개와 분위기 형성이 반복되고, 이동·관찰·입력이라는 핵심 사용법은 한 번도 간단한 절차로 제시되지 않는다. 시작 안내는 분량이 많아서가 아니라 **시간·인원·키트에 비해 실제 플레이 방법이 부족해서** 비효율적이다.

- 권장 첫 안내: 현재 출발 지점 확인 → 키트와 코드 확인 → 목적지로 이동 → 멈춰서 현장 관찰 → 웹에 답 입력.
- 앱의 이동 버튼은 GPS 길찾기나 도착 확인이 아니라 다음 노드 표시다. 목적지명과 다음 단계 안내를 분리할 필요가 있다.
- 이동 중 읽기를 권장하지 말고 각 목적지의 안전한 정지 지점에서 읽고 푸는 흐름으로 표현해야 한다.
- Code의 테스트 코드, Mission의 임시 다음 단계는 처음 보는 사람이 공식 경로라고 받아들일 수 있다.
- Team에 공개 랭킹 표시와 개인정보 입력 자제 문구가 있는 점은 좋다. 다만 2글자 제한과 긴 이름 처리 차이는 사전에 알려야 한다.
- 사전 키트 안내에는 조사 지도가 있지만, 실제 키트의 품질·경로 정보는 저장소에서 확인할 수 없다. 웹 단독 첫 사용자에게 충분하다고 단정할 수 없다.

## 3. Mobile / Outdoor UX

### 3.1 폭별 CSS 분석

| 항목 | 360px | 390px | 430px | 영향 |
|---|---:|---:|---:|---|
| 일반 page 좌우 여백 | 16px | 16px | 18px | 일반 콘텐츠 폭 328 / 358 / 394px |
| h1 | 31px | 31px | 36px | 420px 경계에서 크기와 전체 간격이 갑자기 바뀜 |
| Story 본문 | 16px / 1.95 | 16px / 1.95 | 16px / 2 | 글자 크기는 안정적 |
| page 요소 gap | 24px | 24px | 28px | 좁은 화면도 상당한 수직 여백 |
| 주요 CTA 높이 | 60px 이상 | 60px 이상 | 60px 이상 | 일반 진행 버튼은 누르기 좋음 |
| 단서첩 버튼 최소 높이 | 44px | 44px | 44px | 터치 크기보다 하단 위치가 문제 |
| 매듭 점 버튼 | 22×22px | 22×22px | 22×22px | 폭이 커져도 터치 표적은 커지지 않음 |
| 단서 piece 목록 | 1열 | 1열 | 2열 | 430px에서 단서 이름 줄바꿈과 정보 밀도가 달라짐 |
| 랭킹 시간 표시 | 이름 아래 | 이름 아래 | 같은 행 오른쪽 | 좁은 폭에서 안전한 재배치 |

기본 flex와 max-width는 모바일 대응을 하고 있다. 그러나 데스크톱에서 폭만 줄인 수준을 넘어서려면 현장 입력·길찾기·복귀를 별도로 설계해야 한다.

### 3.2 한 손 조작과 터치

일반 CTA의 60px 높이, 선택지의 54px 이상 높이, 도자기의 3×3 탭 교환은 적절하다. 반면 매듭의 22px 점은 손가락에 가려지고 오탭하기 쉽다. 448×720 이미지에 좌표를 퍼센트로 놓기 때문에 점 간격도 화면 폭에 따라 줄어든다. 예를 들어 L1–R1의 가로 거리는 360px 화면에서 약 30px에 불과하다.

점 버튼을 무조건 44px로 키우면 인접 hit area가 겹칠 수 있다. 확대 가능한 퍼즐 영역, 선택한 점을 크게 표시하는 보조 UI, 겹치지 않는 점 배치 등과 함께 풀어야 한다. 재생 속도 버튼은 최소 34px로 자주 사용하는 주행동보다 작지만, 선택적 기능이라 우선순위는 낮다.

### 3.3 햇빛·이동·긴 스크롤

본문의 밝은 글자와 어두운 배경은 기본 대비가 높다. 다만 실제 햇빛 아래 반사에 대한 적합성을 색상값만으로 입증할 수는 없다. 특히 작은 회색 안내, 어두운 퍼즐 소제목, 저채도 성공 메시지는 실내보다 더 불리할 가능성이 높다.

Story 6은 최소 한 줄씩만 배치해도 본문 line-height 31.2px와 문단 하단 간격 22.4px의 합으로 약 2,570px를 차지한다. 실제 줄바꿈·제목·버튼을 포함하면 더 길다. 고개를 들었다가 다시 읽을 때 현재 문맥을 되찾기 어렵고, 다음 목적지를 확인하려고 스크롤을 반복하게 된다.

### 3.4 뒤로가기와 중단

화면 상태는 React의 screen/flowIndex로 바뀌며 History API나 popstate 처리는 없다. 따라서 브라우저 뒤로가기 제스처를 앱의 이전 단계로 기대하면 실제 결과와 어긋난다. 방문 경로에 따라 웹사이트를 떠날 수 있다.

프로덕션은 node·획득 단서·시간을 저장하지만 정답 초안, 도자기 배치, 매듭 연결, AR 완료는 저장하지 않는다. 개발 모드의 새로고침은 저장을 지우고 Poster로 돌아간다. 이를 실사용 빌드의 동작과 구분해야 한다.

### 3.5 네트워크

- 티저: 75,216,877 bytes, 약 75.2MB. 전체 파일 기준 단순 전송 시간은 5Mbps 약 120초, 10Mbps 약 60초다. 스트리밍 재생 시작 시간이나 실제 사용자 대기시간을 뜻하지는 않는다.
- Story 7 영상: 약 13.4MB.
- 첫 Poster: 약 2.58MB. MaruBuri TTF: 약 3.27MB.
- 미션 3 이미지: 약 3.37MB, 미션 6: 약 2.82MB.
- 티저가 참조하는 /teaser-poster.png는 현재 public 목록에 없다. 재생 전 기대한 썸네일이 제공되지 않을 가능성이 높다.
- StoryVideo는 preload=metadata, playsInline, 재생속도 선택을 제공한다. 반면 teaser에는 명시적인 preload 정책이 없다.
- video의 track, 자막 파일, 실패 시 동등한 대체 텍스트 UI는 코드에 없다. 영상 자체에 자막이 구워져 있는지는 확인하지 못했다.
- service worker나 게임 자산 오프라인 캐시는 구현에서 발견되지 않았다. 일반 HTTP 캐시와 랭킹 localStorage 캐시는 별개다.

Pretendard와 Noto Sans KR은 CSS에 이름만 있고 현재 코드에서 별도 로드하지 않는다. 따라서 모든 기기에서 Pretendard로 보인다고 말할 수 없다. Song Myung과 Gowun Batang은 Google Fonts, MaruBuri는 로컬 TTF를 사용하며 font-display: swap이 설정되어 있다.

폰트 수가 많다는 이유만으로 교체할 필요는 없다. 표제·서사·기능의 세 역할이 이미 있다. 다만 h2용 Gowun과 편지 h2용 MaruBuri처럼 역할이 겹치는 곳은 의도적으로 정리할 필요가 있다. MaruBuri는 Regular 한 굵기만 제공하고 font-synthesis: none이어서 굵은 강조를 기대하는 경우 실제 표현을 확인해야 한다.

권장 사항은 본문 16px 기준을 유지하되 현장 테스트에서 17px와 비교하고, 문단 간격을 의미 단위별로 나누는 것이다. 폰트 교체보다 문단의 길이·간격·대비·보조 라벨의 일관성이 더 큰 문제다.

## 6. Color / Contrast

dark wine / black은 미스터리 분위기를 만들고 gold는 제목·경계·기능 강조를 묶는다. parchment를 이동 서찰과 결과 인증에 선택적으로 쓰는 방향은 유효하다. 현재 본문 전체를 베이지 카드로 둘러싸지 않는 점도 읽기 공간을 확보한다.

문제는 어두운 문서 화면으로 옮겨오면서 일부 요소의 옛 밝은 카드용 색상이 남았다는 것이다.

|---|---:|---|

Code의 주 버튼은 class 없는 58px 규칙을 적용받고 Story 주 버튼은 60px이다. 이 차이는 치명적이지 않지만 동일 계열 행동이 여러 CSS 경로에 나뉘어 있다.

Mission 1 후반에는 선택지 3개, 제출, skip, 단서첩이 동시에 존재한다. 선택지는 답 후보이고 제출은 진행 행동인데, skip은 정답 여부와 무관하게 같은 결과를 낸다. 선택지의 존재보다 **서로 다른 두 완료 경로**가 혼동을 만든다.

우선순위는 정상 제출 1개를 주행동으로 두고, 힌트·단서첩은 언제나 접근 가능한 보조행동으로 정리하는 것이다. 운영용 skip은 사용자 플레이 UI에서 분리해야 한다. 단순히 색을 더 흐리게 하는 것으로 해결되지 않는다.

문자 수는 paragraphs 배열을 공백·문장부호 그대로 이어 붙인 문자열 길이다. 미션 설명과 영상 대사는 포함하지 않는다.

본문 max-width 42rem와 모바일 실폭 328–394px는 한 줄이 과도하게 길어지지 않게 한다. MaruBuri 16px와 1.95–2의 line-height는 단독 문장 읽기에 여유가 있다. 그러나 문장 한두 개를 계속 독립 p로 두고 각 p에 1.4em 여백을 더해, **문자 수보다 문단 수가 화면 길이를 지배**한다.

Story 6은 Story 4보다 글자 수가 적지만 문단은 12개 더 많다. 깨진 도자기, 끊어진 매듭, 도자기를 깨뜨리고 같은 짧은 문장을 모두 같은 하단 여백으로 처리하면 극적 호흡보다 반복 스와이프가 더 크게 느껴질 수 있다.

- Callout 컴포넌트는 있으나 실제 calloutParagraphIndexes는 프롤로그의 한 문장에만 지정되어 있다. 나머지 중요한 편지 문구는 일반 본문과 같은 비중이다.
- Story renderer에 위치 metadata 지원은 있지만 현재 story 노드들은 location을 사용하지 않는다. 지원 코드가 있다는 사실만으로 실제 위치가 표시된다고 평가할 수 없다.
- Story 7의 mediaNote 표시 분기도 있지만 현재 데이터에는 사용되지 않는다.
- Story 7 영상은 다음 버튼을 막지 않아 재생 실패가 즉시 navigation blocker가 되지는 않는다. 다만 텍스트 76자만으로 영상의 핵심 전부가 전달되는지는 영상 내용 확인이 필요하다.
- 다음 버튼은 긴 본문 뒤에 있어 순서대로 읽기를 유도한다. 반면 다음 목적지 확인이나 이미 읽은 장 재방문에는 비효율적이다.
- 이전 스토리 재열람은 없다. 실수로 다음을 누르면 본문을 다시 찾을 경로가 없다.

### 새 노드의 읽기 시작

현재 useLayoutEffect는 화면 또는 flow 노드 id의 실제 변경에만 반응해 렌더 commit 뒤 document를 top으로 이동시킨다. 정상 Mission → Story, Story → Mission, Mission 7 → Ending, Ending → Clear 전환의 제목 누락 문제를 해결하는 구조다. 입력, timer, choice 변경에는 실행되지 않는다.

이것은 장점이다. 다만 scroll reset은 제목 focus 이동이나 스크린리더의 새 화면 안내까지 해결하지 않는다. 단서첩 복귀도 top으로 가므로 같은 긴 스토리를 읽던 문맥은 잃는다. 최초 저장 상태 복원 시에는 previousNavigation이 없어서 의도적 scroll reset을 건너뛰므로, 브라우저 자체 복원 결과는 별도 확인 대상이다.

## 9. Movement Guide

movementLetter는 현재 **Mission 1에서만** 사용한다. 연한 parchment 면, 낮은 4px radius, 도장 같은 원형 pseudo-element, MaruBuri 본문이 일반 dark 문서와 명확히 다르다. 반복 카드 속 작은 장식이 아니라 밝은 면 전체가 바뀌므로 특별한 서찰로 느껴지게 할 근거는 충분하다.

다만 밝은 서찰은 6문단이고, 길찾기 목적의 정보는 향기도예라는 이름 하나다. 위치명은 첫머리에 있어 찾기 쉽지만 주소·지도 연결·실물 표지·어디에서 볼지는 없다. 장식이 지나치다는 문제보다 **서사 밀도에 비해 실제 이동 정보가 적다**는 문제가 크다.

사용자가 설명한 설정은 서화의 특별한 이동 안내지만 현재 UI에는 발신자 이름이나 서명이 없다. 제목은 플레이어가 받은 서찰이고 내용은 전하와 제가 함께 고른 물건이다. 실제 저자가 누구인지 화면만으로는 확정할 수 없으며, 서화의 편지라는 설정이 플레이어에게 전달된다고 보기 어렵다. 의도된 정체 은폐라면 숨김이 서사상 일관되어야 하고, 특정 인물의 안내로 알아야 한다면 그 단서가 필요하다.

권장 구조는 봉서의 정서를 유지하면서 첫머리에 목적지·어디를 관찰할지·종이지도 어느 표시를 볼지를 짧게 묶는 것이다. 장소 자체를 찾는 미션 7은 정확한 답 위치를 노출하지 말고, 탐색 범위와 안전한 관찰 지점까지만 안내한다.

## 10. Case Record

사건 기록은 미션마다 documentSection caseRecord로 나타난다. 밝은 카드 대신 투명 배경·얇은 금색 선·밝은 본문을 사용해 스토리를 해치지 않는 보조 문서로 만든 점은 좋다.

반면 사건 기록에 상단 divider가 있고 h2 아래에도 divider가 있다. 그 위에 이동 안내, 아래에 조사 문제가 각각 영어 라벨과 제목으로 시작하므로 미션마다 문서의 머리말을 반복해서 통과한다. Mission 1은 사건 기록만 5문단이며 서찰까지 읽고 나서 퍼즐에 도달한다.

Mission 2 이후에는 대체로 짧은 intro 한 문단이라 모두를 과도하게 길다고 볼 수 없다. 문제는 내용에 비해 반복되는 제목·선·여백의 비용이 크다는 점이다. 최초에는 펼쳐 두고 재방문에는 접을 수 있는 사건 기록, 또는 이동 목적과 관찰 대상을 먼저 요약하는 방식이 낫다. 기록 자체를 삭제할 필요는 없다.

## 11. Mission / Puzzle UX

### Mission 1 — 도자기 교환 → 간판 확인 → 선택형 추리

**장점:** 드래그가 아닌 두 번 탭으로 조각을 바꾸므로 손가락으로 원본을 오래 가릴 필요가 없다. 선택 상태의 테두리 변화, 복원 완료 메시지, 답 미선택 시 제출 비활성화가 있다.

**문제:**

1. 복원·현장 카메라·추리의 세 단계가 처음에는 보이지 않는다. 복원하면 끝일 것으로 기대한 사용자는 새 필수 단계가 반복해서 등장한다고 느낄 수 있다.
2. 정확한 탭 조작 안내가 퍼즐 아래 smallText에 있고 색도 어둡다. 처음에는 드래그를 시도할 가능성이 있다.
3. 퍼즐 완료와 동시에 ARScanGate가 mount되며 카메라 권한을 요청한다. 사용자가 지금 카메라가 필요한 이유를 읽기 전에 권한 창이 뜰 수 있다.
4. AR은 카메라 프레임과 기준 이미지의 유사도 비교다. 실제 현장에서 왜 실패했는지 유사도 숫자만으로 판단하기 어렵다.
5. 카메라 권한 오류 또는 비교 불일치 3회에는 수동 진행이 나온다. **기준 이미지 네트워크 오류는 catch에서 문구만 보여주고 failCount를 늘리지 않아 이 우회 경로를 열지 못한다.** 정상 카메라+기준 자산 실패 조합에서 반복 실패가 가능하다.
6. 기준 간판 이미지는 423×91, 약 4.65:1인데 비교 crop은 320×203, 약 1.58:1이다. overlay와 guide의 가로·세로 비율도 다르다. 실제 인식률은 측정하지 않았지만 사용자가 맞춘 모습과 비교 영역이 일치하는지 현장 확인이 필요하다.
7. 수동 진행 버튼의 인식이 계속 실패합니다라는 문구는 결과보다 불만 표현에 가깝다. 카메라 없이 현장에서 확인하고 계속하기처럼 결과를 예측하게 해야 한다.
8. 선택 문제 h3, AR h3, AR 점수에 어두운 ink가 적용되는 문제를 우선 고쳐야 한다.

단계 안내를 복원 → 간판 확인 → 추리로 미리 보여주고, 모든 기술적 실패에서 동등한 수동 확인을 제공하는 것이 좋다. 같은 노드 내부에 단계가 추가될 때 전체 top reset은 필요 없지만 새 영역으로의 focus/알림은 검토할 수 있다.

### Mission 2 — 매듭 연결

**확정된 핵심 결함:** 안내는 왼쪽과 오른쪽을 한 쌍씩 이으라고 하지만 정답 키는 방향성을 갖는다. R1→L1은 맞고 L1→R1은 틀리며, L2→R2는 맞는 식으로 시작 방향이 쌍마다 다르다. 정답은 쌍의 순서 자체까지 강제하지는 않지만, **각 쌍에서 어느 점을 먼저 누르는지**를 강제한다. 직접 확인한 바탕 이미지는 찢어진 주머니이며 시작 방향을 명시하는 화살표·번호가 없다. 이미지의 찢김 형상에서 방향을 추론하게 의도했는지는 별도 확인이 필요하지만, 현재 규칙 문구와 점 버튼 자체는 이를 설명하지 않는다.

따라서 안내를 정확히 따른 사용자도 틀릴 수 있다. 오답 메시지는 실의 방향이 어긋났다고 알려주지만 그때는 이미 650ms 뒤 전체 연결을 지우도록 예약한다. 학습되지 않은 규칙과 22px 터치 표적, 전부 초기화하는 처벌이 결합된다. 이것은 취향이 아니라 P0 진행성 문제다.

정방향 바느질 자체가 추리라면 시작 방향을 알 수 있는 단서와 설명을 제공해야 한다. 그런 의도가 없다면 양방향 연결을 같은 쌍으로 취급해야 한다. 부분 오답은 해당 연결만 취소하고 이미 맞춘 연결은 보존하는 방식을 우선 검토한다.

근거: [정답 쌍](../src/App.jsx#L273), [방향 키와 판정](../src/App.jsx#L958), [전체 초기화](../src/App.jsx#L1035), [22px 버튼](../src/styles.css#L595).

### Mission 3 — 현장 문양을 네 자리 숫자로

관찰 위치, 기준 조각, 읽는 방향, 문양→숫자 변환이 명시되어 있어 앱과 현장의 연결이 비교적 명확하다. 반면 이미지 자체는 답이 아닌 현장 찾기용이라는 중요한 설명이 렌더되지 않는 hints 안에 있다. 현장 사용자는 사진에서 바로 정답을 찾으려 할 수 있다.

숫자 문제인데 inputMode나 숫자 입력 안내를 필드에 적용하지 않는다. 네 자리 입력 예시·오류 시 형식 확인을 제공하면 추리 오답과 입력 실수를 구분할 수 있다.

### Mission 4 — 가로등 관찰·순서 변환

이전 답 1245를 본문에 다시 제시하여 암기 부담을 줄인 점은 좋다. 정면만 보라는 지시는 관찰 대상을 제한한다. 하지만 가로등이라는 장소명만으로 어느 가로등인지 충분한지는 종이지도와 현장 구성을 확인해야 한다.

항목 1·2·3·4·5 중 3을 제외하고 1245 순서로 수량을 읽는 이중 변환이다. 이는 퍼즐의 난도일 수 있으므로 무조건 삭제할 대상은 아니다. 항목표와 입력창을 한눈에 비교할 수 있게 하고, 막혔을 때 단계별 힌트를 제공하는 것이 적합하다. 실제 장식과 정답 8888이 일치하는지는 저장소만으로 확인할 수 없다.

### Mission 5 — 현장 색 순서→문장

텍스트와 참고 이미지가 순서대로 나오는 contentBlocks는 설명을 해당 그림 옆에서 읽게 한다는 장점이 있다. 그러나 상단 문양 이미지, 데크 꽃 이미지, 색상 변환표, 정답 입력이 수직으로 나뉘어 360px에서는 비교를 위해 왕복 스크롤할 수 있다.

색 이름 대신 대응 단어를 입력해야 한다는 규칙이 있고, 정답은 공백을 무시한다. 그 허용 조건은 hints에만 있어 UI에서 알기 어렵다. 색 구분이 어려운 사용자나 꽃 상태·조명이 달라졌을 때 쓸 보조 단서가 필요하다. 실제 꽃이 변동하는지, 이미지가 현장 관찰을 대체해 버리는지는 현장 확인 항목이다.

### Mission 6 — 벽화에서 반복된 동물 찾기

대상을 좁히는 지시가 단계적이며 닭/수탉을 모두 허용하는 점이 좋다. 다만 벽화를 찾는 데 실패하면 힌트 UI가 없고, 참고 이미지 외에 탐색 범위가 없다. 숫자 문제와 같은 일반 입력창을 쓰더라도 동물 이름을 입력한다는 필드 라벨이 있으면 더 명확하다.

### Mission 7 — 장소 수수께끼→영물

최종 현장 탐색을 웹 정답과 연결하는 구조는 장르에 맞는다. 하지만 텍스트 단서만으로 골목을 찾는 데 실패했을 때 안전하게 범위를 좁혀 줄 힌트가 없다. 장소 수수께끼를 없애는 대신 단계적으로 지역·외관·상징을 밝히는 도움 경로가 필요하다.

### 모든 미션의 공통 문제

- hints 배열, openHint, isHintOpen은 있으나 실제 힌트 버튼·내용을 렌더하지 않는다. Landing의 힌트 사용 안내와 Clear의 힌트 평가가 현재 기능과 맞지 않는다.
- 잘못된 답에는 공통 오류 문구가 나오고 입력은 유지된다. 유지되는 것은 좋지만, 문구는 skip 아래에 있어 모바일 키보드/viewport에 따라 놓칠 수 있다. aria-live나 필드와의 오류 연결도 없다.
- 정답이면 completeCurrentMission이 곧바로 다음 노드로 간다. 정답 승인·무엇을 획득했는지·현재 완료 수를 별도로 확인할 시간이 없다.
- TEMP skip은 실제 성공과 동일한 완료 함수로 시간과 pieces를 기록한다. 따라서 결과·랭킹·보상에서 정상 플레이와 구분되지 않는다.
- 입력에는 명시적인 label, 형식별 inputMode, enterKeyHint, form submit이 없다. 키보드 완료 키로 제출을 기대하는 사용성은 확인·보완해야 한다.
- 빈 답도 일반 오류로 처리한다. 빈 입력, 형식 오류, 추리 오답을 구분하면 불필요한 좌절을 줄인다.

## 12. Clue Notebook

현재 단서첩의 실제 역할은 **미션별 수집 현황표**다. 지도, 사건 기록 보관, 과거 추리 재검토 기능은 아니다.

발견 가능성은 낮다. Story, Mission, Ending의 맨 아래에만 버튼이 있고 고정 헤더에서는 열 수 없다. 길어진 본문 중간에서 막혔을 때 가장 필요한 도구에 접근하려면 끝까지 이동해야 한다. 반면 작은 금색 utility 표현과 44px 높이로 주 CTA와 구분한 것은 좋다.

열어볼 동기도 약하다. 새 단서 배지, 방금 수집한 물건의 미리보기, 3/7처럼 획득 기반 숫자가 버튼에 없다. 안에는 조사 목록과 획득 단서 이름이 두 번 나오지만 내용 자세히 보기나 다시 읽기가 안 된다. 아직 닫힌 미션의 제목도 표시하므로 미스터리의 단서 이름을 어디까지 공개할지 의도 확인이 필요하다.

공방거리 조사 지도라는 제목 아래 실제로 나오는 것은 미션 번호·제목·상태뿐이다. 현재 위치, 공방명, 주소, 길 연결이 없어서 길찾기를 기대하고 누른 사용자에게 기대 불일치가 생긴다. 지도 기능을 추가하지 않는다면 제목을 조사 현황으로 바꾸는 편이 정직하다.

### 복귀의 실제 상태

- 진입과 복귀 모두 screen 변경으로 top reset한다.
- flow 분기가 사라질 때 TileSwapPuzzle·StitchConnectPuzzle는 unmount된다.
- 도자기 배치·선택, 매듭 연결·선택·오답 상태는 각 자식의 useState라 다시 돌아오면 초기 상태가 된다.
- 반면 App의 missionPuzzleSolved, arScanDone, answer는 같은 node에서 유지된다.
- 결과적으로 **중간 풀이 소실**뿐 아니라 **퍼즐은 초기 모습인데 완료 메시지/제출 경로는 남는 불일치**가 가능하다.
- 새로고침에는 이 부모의 미션 중간 플래그도 저장되지 않는다.

이것은 단순 스크롤 취향 문제가 아니다. 보조 도구를 사용한 대가로 작업을 잃으면 사용자는 단서첩을 피하게 된다. 단서첩 개선의 첫 순서는 접근 버튼 확대가 아니라 상태 보존이다. 그다음 읽던 위치 복귀와 단서 재열람을 추가한다.

## 13. Progress / Timer

sticky 헤더의 4px 진행 bar, 12–13px 메타, tabular-nums 시간은 공간을 과하게 쓰지 않으면서 현재 진행을 계속 보여준다. 시간과 진행률을 큰 카드로 만들지 않은 점은 적절하다.

해석은 부족하다. 진행 3/16이 Mission 1, 15/16이 Mission 7, 16/16이 Ending이다. 사용자는 7개 장소/미션을 진행한다고 느끼는데 시스템은 영상과 이야기까지 같은 한 단계로 센다. 막 도착한 미션에서도 해당 노드가 분자에 포함되어, 완료한 미션 비율과 다르다. 스토리 길이와 장소 이동 시간도 같지 않으므로 남은 시간으로 해석할 수 없다.

추천 표시는 미션 2/7 또는 단서 1/7과 이야기 장 정보를 구분하는 것이다. 진행 bar를 유지한다면 이야기 진행이라고 명시할 필요가 있다. AR 3단계는 전체 진행과 별도로 보여주는 편이 이해하기 쉽다.

타이머는 teaser를 떠날 때 시작하고 Mission 7 완료에 고정된다. 프롤로그 읽기, 길찾기, 단서첩 체류, 앱을 배경으로 보낸 시간까지 포함되며 Ending 읽기는 제외된다. 이 규칙을 시작 전에 알려주지 않아 기록 경쟁을 원하는 사용자와 느긋한 감상을 원하는 사용자 모두 기준을 알기 어렵다.

또한 공방 성향은 1·2·3·5 미션 중 가장 짧은 경과시간으로 정한다. 그 시간에는 이동·읽기·카메라·기기 사용이 섞여 있다. 도예 판별 능력이나 취향을 정확하게 측정했다고 설명하기에는 근거가 약하다. 재미용 추천이라는 표현과 실제 사용자 선택을 병행하는 것이 더 신뢰할 만하다.

## 14. Ending

진입 시 ENDING 라벨, 혼례의 진실 제목, 일반 문서와 다른 배경 이미지 카드, 특별한 클리어 인증 버튼이 있다. 따라서 아무 표식 없이 일반 story가 계속된다고 느끼는 수준은 아니다. 마지막 미션에서 타이머가 멈추고 top reset이 되는 것도 결말 전환을 돕는다.

다만 최상단에 7개 단서를 모두 모았다는 성취 정보는 없고 header도 평소 flow의 연속이다. ENDING이 문서 밖과 카드 pseudo-element에 두 번 나온다. 카드의 ::before는 top:20px인데 모바일 padding-top은 26px라 첫 문단과 가까운 공간에 놓인다. 겹침 여부는 렌더 확인 대상이다.

더 큰 문제는 46문단을 단일 .endingCard 안에 넣고 전체 카드 높이에 background-size: cover를 적용한 것이다. 원본 포스터는 1672×941 가로 이미지다. 수천 px가 될 수 있는 세로 카드에 cover로 채우면 가로 이미지가 크게 잘려 인물·구도가 의도대로 보이지 않을 가능성이 높다. 그라디언트 역시 카드 전체 높이에 비례하므로 위쪽 여러 문단은 어두운 덮개가 상대적으로 약한 영역 위에 놓인다.

짧은 고정 비율의 결말 Hero와 별도 읽기 본문을 분리하면 이미지를 의미 있게 보여주면서 긴 서사를 보존할 수 있다. 진입 순간의 모든 조사 완료 상태, 결말 제목, 이어지는 인증 CTA가 세 역할을 나누는 것이 좋다.

## 15. Clear / Truth Reveal

Clear의 .clearRevealHero는 220–280px 최소 높이에 이미지와 별도 overlay를 둬 Ending의 거대한 배경 카드보다 구조가 안정적이다. 개인 이름·시간·힌트·칭호를 인증서로 보여주는 것도 일반 story와 다른 역할이 있다.

하지만 첫 인상은 진실 확인, 이어지는 Final Letter와 사건 요약이다. Ending에서 이미 진실과 인물의 결말을 긴 분량으로 읽은 뒤라 다시 결말을 읽는 느낌이 날 가능성이 높다. 개인 성과는 세 번째 덩어리에서 시작한다. 똑같은 story7-poster가 Story 7 → Ending → Clear에 재사용되는 것도 결말 단계 간 구별을 약하게 한다.

개인 인증이 주역이면 최상단을 조사 완료 + 조사관 이름 + 핵심 기록으로 구성하고, 진실 요약은 선택적으로 재열람하게 하는 편이 낫다. 공방 추천은 그다음, 실제 보상은 추천보다 빠르게 찾을 수 있어야 한다.

처음부터 다시 하기는 쿠폰 CTA 바로 뒤에 있고 즉시 localStorage의 게임 기록을 제거한다. 확인이나 되돌리기가 없어 잘못 누르면 쿠폰 화면으로 돌아갈 앱 경로를 잃을 수 있다. 랭킹의 이미 제출된 기록까지 삭제하는 함수는 아니므로 두 데이터를 혼동해서는 안 된다.

랭킹 제출 실패 시 클리어 인증은 유지된다고 명시하는 문구는 좋은 실패 격리다. 다만 저장 중 상태가 오래 지속될 경우의 재시도·소요 상태 안내는 부족하다.

## 16. Reward / Coupon

쿠폰이라는 사실은 Reward Coupon, 특별 쿠폰, 방탈출 클리어 인증, 사용처·기한으로 충분히 전달한다. 화면 제시와 직원 확인 방식, 바코드가 없다는 설명도 실제 행동을 알려주는 장점이다.

그러나 **혜택의 내용이 없다.** 할인 금액·비율인지, 증정인지, 어떤 체험에 적용되는지, 추가 구매 조건이 있는지 알 수 없다. 혜택을 받을 수 있다는 약속만으로는 보상 크기를 판단하거나 매장까지 더 걸어갈 동기가 생기기 어렵다. 조건을 임의로 만들지 말고 운영자가 확정한 내용을 표시해야 한다.

메리골드의 주소·지도·운영시간·직원에게 보여줄 핵심 정보 우선순위도 없다. 스크린샷이 인정되는지, 현재 웹 화면이 필요한지 명시되지 않았다. 따라서 스크린샷 저장 버튼을 먼저 만드는 것보다 제시 정책을 확인해야 한다.

기한은 발급/클리어 날짜가 아니라 getCouponExpireDateText에서 **현재 날짜 기준 다음 달의 같은 날짜**로 매번 계산한다. 다음 날 다시 열면 날짜도 달라진다. 고정된 쿠폰 유효기간처럼 읽히는 UI와 실제 계산이 맞지 않으며 직원과 사용자 사이의 혼동 가능성이 있다.

Ticket 느낌은 dashed inner frame·stamp box·분리된 사용 정보로 충분한 의도가 있다. 다만 좁은 화면에 couponInfoBox의 두 열, 긴 날짜, 긴 팀명을 넣으면 줄바꿈을 확인해야 한다. 팀명 입력에는 최대 길이가 없고 랭킹 서비스만 20자로 자르므로 인증/쿠폰과 랭킹의 이름도 달라질 수 있다.

쿠폰 아래 가장 강한 버튼은 오늘의 조사 랭킹 보기다. 보상 사용이 제품의 마지막 행동이라면 매장 찾아가기나 직원 제시 모드를 우선하고 랭킹은 보조로 내리는 편이 맞다.

## 17. Consistency

### 의도적 차이로 볼 수 있는 것

- Poster의 full viewport 이미지와 Landing의 소개 Hero: 몰입 입구와 실제 안내라는 역할 차이는 있다. 다만 둘 다 통과하도록 강제할 효용은 다시 검토해야 한다.
- dark 문서와 밝은 movementLetter: 외부에서 받은 특별한 서찰을 구분한다.
- 결과 인증서의 parchment와 쿠폰의 어두운 티켓: 기록과 실물 제시용 보상을 구분한다.
- endingAction의 별표와 rewardAction의 절취선: 결말 인증과 보상의 의미 차이를 드러낸다.
- 일반 본문의 MaruBuri와 규칙·입력의 sans-serif: 감상과 조작 모드를 나눈다.
- 작은 화면에서 랭킹 시간을 다음 줄로 보내는 방식: 좁은 폭의 명시적 대응이다.

### 누적 CSS나 구조에서 발생한 불일치

- .page, .storyText, .clueNotebookTrigger, .missionProgressMeta가 후반부에서 여러 번 재선언된다. 이것만으로 나쁘다고 판단하지 않지만, 실제로 nested h3·successMessage·단서 row 색이 새 dark surface에 맞게 보정되지 않았다.
- card 22px, choice 16px, puzzle image 18px, letter/piece 4px, ending 2px, main start pill이 공존한다. 서찰·티켓의 각진 형태는 설명되지만 일반 카드와 새 문서 화면 간 경계는 정리되지 않았다.
- page gap, section padding-bottom, p margin, button margin을 동시에 적용해 같은 중요도의 요소 간 거리도 조합에 따라 커진다. 예를 들어 단서첩은 page gap 외에 margin-top 24px를 다시 갖는다.
- Mission 번호 표기는 1·2·3·5에는 있고 4·6은 길거리 실마리, 7은 마지막 길거리 실마리로 바뀐다. 분위기용 chapter와 일관된 미션 번호를 분리할 필요가 있다.
- Landing은 emoji, 단서첩은 ◇·↗, Ending은 ✦를 사용한다. 심각한 기능 문제는 아니지만 emoji의 기기별 표현과 나머지 문서 아이콘의 톤은 다르다.
- StoryVideo·missionImage는 둥근 프레임, clear hero는 4px, ending은 2px다. 역할 기반의 차이는 인정할 수 있으나 같은 이미지가 세 번 쓰이는 경우 역할 구별은 약해진다.
- html lang=en과 페이지 title=marigold-escape는 한국어 작품의 언어·브라우저 제목과 맞지 않는다. 번역/음성 읽기/탭 재발견에 불리하다.
- 실제 storyFlow와 사용하지 않는 data/gameData.js의 storyFlow가 따로 있어 콘텐츠 수정자가 잘못된 쪽을 바꿀 위험이 있다. 현재 사용자 화면 문제와 구분해서 유지보수 과제로 기록한다.

전체 디자인을 다시 만드는 것보다 surface별 텍스트 규칙, 버튼 역할, 간격 단계, 카드 유형의 사용 기준을 작게 정의하는 편이 효과가 크다.

## 19. Strengths — 유지할 가치가 있는 구현

1. **노드 전환에만 적용되는 top reset.** screen과 currentNode.id를 비교하므로 미션 다음 스토리를 제목부터 읽는 구조가 있다. timer와 정답 입력으로 페이지가 튀지 않는다. [App effect](../src/App.jsx#L1573)
2. **주요 조작 버튼의 충분한 높이.** Story 진행·미션 제출·AR 판정은 60px 계열로 묶였다. 한 손 조작에서 작은 텍스트 링크만 제공하는 UI보다 안정적이다. [최종 버튼 규칙](../src/styles.css#L2117)
3. **드래그 대신 탭 교환.** TileSwapPuzzle는 두 조각을 눌러 교환하므로 정교한 드래그나 drop 판정을 요구하지 않는다. 손가락이 퍼즐 내용을 계속 가리지 않는다. [TileSwapPuzzle](../src/App.jsx#L866)
4. **관찰 절차를 구체화한 미션.** Mission 3의 기준 조각·방향·숫자화, Mission 4의 정면만 보기, Mission 5의 텍스트와 이미지 순서는 사용자의 관찰 범위를 제한한다. 난도와 무관한 헤맴을 줄이는 구조다.
5. **입력 오차에 대한 일부 관용.** 공백·대소문자 정규화, 닭/수탉과 용/룡의 허용은 추리와 무관한 입력 실패를 줄인다. [normalizeAnswer](../src/App.jsx#L789)
6. **부분적인 현장 실패 대안.** 카메라 권한 실패와 비교 불일치 누적에는 수동 진행이 있다. 커버하지 못한 예외가 있지만 현장 환경을 완전히 이상적인 것으로 가정하지는 않았다. [ARScanGate](../src/App.jsx#L1347)
7. **랭킹과 클리어 인증의 분리.** 제출 오류가 나도 인증이 유지된다는 안내가 있으며 랭킹 조회에는 날짜별 localStorage 캐시를 활용한다. 외부 서비스 실패를 게임 성공 전체의 실패로 표현하지 않는다. [rankingService](../src/utils/rankingService.js), [RankingBoard](../src/components/RankingBoard.jsx)
8. **기본 서사/기능 폰트 역할 구분.** MaruBuri 서사와 sans 기능 UI는 목적이 다르다. 무조건 한 폰트로 통일할 이유가 없다.
9. **결말·보상 CTA의 의미 있는 차이.** 별표와 절취선은 장식의 대상이 결말 인증과 쿠폰이라는 점에서 기능과 연결된다.
10. **현장 주의사항의 명시.** 횡단 시 화면을 보지 말 것, 매장 영업을 방해하지 말 것, 개인정보를 이름에 넣지 말 것 등을 안내한다. 실제 반복 플레이 흐름 안으로 연결하면 효과가 더 커진다.

## 22. 우선순위

### P0 — 정상 플레이를 방해하거나 작업을 잃게 하는 문제

1. **A01+A02: Mission 2 안내–판정 불일치와 작은 표적/전체 초기화.** 독립적인 사용자에게 설명하지 않은 규칙으로 실패시킨다.
2. **A03: 단서첩 왕복 시 퍼즐 상태 소실과 완료 상태 불일치.** 보조 화면이 실제 작업을 지운다.
3. **A04: 힌트 진입 부재.** 힌트를 약속한 야외 방탈출에 정상적인 막힘 해소 경로가 없다.
4. **A06: 질문·AR·단서 상태의 핵심 텍스트 색 충돌.** 기능 이해에 필요한 텍스트가 배경에 묻힌다. 일반 미적 polish와 구분한다.
5. **A07: 사용자 화면에 테스트 skip 노출.** 실제 성공과 동일한 결과를 기록한다. 공개 운영 전 해결해야 한다.
6. **A05: AR 기준 이미지/기술적 예외에서 수동 경로 부재.** 해당 오류 발생 시 진행을 막는 조건부 P0다.
7. **A08: 완료 화면의 확인 없는 재시작.** 실수 한 번이 쿠폰 접근 기반을 제거하는 데이터 손실성 행동이다.

테스트 운영만 하는 동안에도 A01–A06은 관찰할 사용자 경험을 왜곡한다. skip이 있다고 다른 진행 결함이 해결된 것으로 볼 수 없다.

### P1 — 체감 UX 개선이 큰 작업

- **A09·A10:** 시작 방법과 이동 → 관찰 → 입력 흐름을 명시하고 실제 목적지 안내를 보강한다.
- **A11·A12:** 긴 독서의 문단/여백을 조정하고 현장 정답 입력·오류 피드백을 개선한다.
- **A13·A14·A15:** 성공/수집 피드백, 단서첩의 재열람 가치, 7미션 기준 진행 정보를 정리한다.
- **A16:** 브라우저 뒤로가기와 중단/재개를 정상 여정에 포함한다.
- **A17·A18·A19:** Ending은 결말, Clear는 내 성과, Coupon은 구체적인 보상 사용으로 역할을 분리한다.
- **A20·A21:** 네트워크·무음·보조기기에서도 기본 진행과 내용 이해가 가능하도록 한다.
- **A22:** 쿠폰에서 랭킹을 보고 바로 복귀할 수 있게 하고 실패 시 재시도를 제공한다.

A19의 날짜 문제는 표시만 다듬는 일이 아니다. 운영 정책과 고정된 발급 기준을 함께 확정해야 한다.

### P2 — Visual polish

- A24 중 카드/radius/간격/라벨의 역할 정리.
- 이동 서찰의 발신자 표현, 범용 영어 라벨 크기와 명조 사용 범위의 일관성.
- emoji·도형 아이콘의 표현 방식 정돈.
- secondary 버튼이 dark 화면에서 과하게 튀는 시각적 무게 조정.
- 작품 이름으로 브라우저 title·소셜 소개 등 기본 브랜드 정보 정리. 단, lang은 접근성 기능 문제로 P1에 포함한다.
- A23 중 추천 성향의 근거 설명과 명칭 조정.

### P3 — 있으면 좋은 개선

- 혜택 정책을 확정한 뒤 인증/쿠폰 저장·공유 기능.
- 최근 읽은 기록 북마크, 선택적 본문 크기 조절.
- 환경 테스트 결과에 따라 outdoor 읽기 모드.
- 전체 자산의 오프라인 패키지, 선택적 다운로드.
- 지도와 거리/예상 이동시간을 풍부하게 제공하는 확장 기능. 단, 현재 목적지와 탐색 범위를 알리는 최소 안내는 P1이다.
- 동료와 공유하는 팀 단서첩, 취향 선택 기반 공방 추천.

P3 확장은 현재 문제의 선행 해결책이 아니다. 오프라인 전체 패키지를 만들기 전에도 네트워크 실패에서 도움받고 재개할 수 있어야 한다.

## 지금 당장 수정해야 하는 5가지

1. **매듭 퍼즐의 안내·정답 판정·터치 영역을 일치시킨다.** 설명에 없는 방향 실패와 전체 초기화를 해소하고, 한 손으로 누를 수 있는 선택 방식을 만든다.
2. **단서첩을 열어도 풀이가 보존되게 한다.** 도자기/매듭의 중간 상태와 solved/AR 완료 상태가 일관되게 복원되어야 한다.
3. **막혔을 때 정상적으로 회복할 경로를 제공한다.** 실제 힌트 버튼을 연결하고 카메라·기준 이미지 실패 모두에서 수동 확인과 재시도가 가능하게 한다.
4. **필수 텍스트의 색 충돌을 고친다.** Mission 1 질문·AR 수치, 퍼즐 조작/성공 안내, 단서첩 current/cleared/locked를 먼저 확인한다.
5. **실사용 경로에서 임시 skip을 분리한다.** 문제를 푼 결과와 테스트 통과를 같은 수집·기록·보상으로 처리하지 않게 한다.
